# Рефакторинг скрипта интеграции подразделений из 1С (`import.php`)

## 1. Аудит исходного кода

### 1.1. Дисковая подсистема (I/O Bottleneck)
* **Сканирование директорий в цикле.** `logToFile()` вызывалась для каждого пользователя и при каждом вызове выполняла `scandir()` всей папки логов с проверкой дат. При 1000 записей это 1000 лишних обращений к файловой системе.
* **Частые операции записи.** `file_put_contents()` открывал и закрывал файл на каждой итерации цикла вместо буферизированной записи.
* **Дробление логов.** Шаблон имени файла с секундами (`date('H:i:s')`) создавал десятки мелких файлов за один цикл импорта.

### 1.2. Нагрузка на MySQL (проблема N+1)
* **Одиночные запросы в цикле.** Последовательный вызов `$DivisionUpdaterHelper->addCodesBy1C()` генерировал 2–3 отдельных SQL-запроса на каждого пользователя (`SELECT`, `UPDATE`, сброс кеша). На больших пакетах это тысячи запросов за выгрузку.
* **Лишние записи в БД.** Поля перезаписывались даже для пользователей, у которых код подразделения не изменился.

### 1.3. Архитектура и производительность
* **Синхронная обработка в HTTP-запросе.** Весь пакет обрабатывался в одном веб-процессе, что на больших объёмах приводит к обрыву по таймауту и частичному обновлению данных.
* **Избыточная инициализация ядра.** `prolog_before.php` подключался без служебных констант (`NO_KEEP_STATISTIC`, `NOT_CHECK_PERMISSIONS`, `STOP_STATISTICS`), запуская веб-аналитику и лишние проверки при фоновом обмене.

### 1.4. Безопасность
* **Отсутствие авторизации.** скрипт импорта мог принимать (в случае отсутствия защиты на других уровнях) запросы без проверки метода и токена.
* **Публичные логи.** Файлы сохранялись внутри `DOCUMENT_ROOT` с правами `0777` и были доступны по прямой ссылке.
* **Отсутствие обработки ошибок.** Не проверялся синтаксис JSON (`json_last_error()`), отсутствовали `try-catch` и корректные HTTP-статусы ответа.

## 2. Реализованные решения

Код переведён на **асинхронную очередь с пакетной обработкой** штатными средствами Битрикс (PHP 8.2 / MySQL 8.2).

### 2.1. Асинхронная архитектура (Webhook + Highload-блок + Cron)
* **HTTP-приёмник (`import.php`):** проверяет метод и Bearer-токен, валидирует JSON, записывает пакет в очередь Highload-блока `DivisionImportQueue` одним `INSERT` и сразу возвращает `202 Accepted`.
* **CLI-воркер (`worker.php`):** запускается по `cron` и разбирает очередь в фоне без ограничений HTTP-таймаутов.
* **Защита от наложения процессов:** воркер использует файловую блокировку `flock()`.

### 2.2. Пакетная работа с БД (`DivisionBatchUpdater`)
* **Разбиение на порции данных:** пакет делится на чанки по 500 записей (`array_chunk`).
* **Пакетная выборка:** все пользователи чанка выбираются одним запросом через `Bitrix\Main\UserTable::getList()` с фильтром `'@LOGIN'`.
* **Фильтрация изменений:** в обновление попадают только записи, где новый код отличается от текущего `UF_CODE` в БД.
* **Групповой SQL UPDATE:** данные в `b_uts_user` обновляются одним запросом `UPDATE ... SET UF_CODE = CASE VALUE_ID ... END WHERE VALUE_ID IN (...)`. Количество запросов к БД на 10 000 пользователей сокращено с ~30 000 до ~40.
* **Два режима обновления:** В качестве альтернативы предусмотрен updateViaBitrixApi() через штатный CUser::Update() (с предварительной пакетной выборкой и отсевом неизменившихся записей) — на случай, если в проекте завязана бизнес-логика на события OnAfterUserUpdate.


### 2.3. Буферизированное логирование (`Logger`)
* **Запись за одну операцию:** сообщения копятся в памяти и сбрасываются на диск одним вызовом `file_put_contents()` с `LOCK_EX` при завершении скрипта.
* **Вынос ротации в Cron:** `Logger::rotateLogs()` вызывается раз в сутки из CLI-воркера. Файлы группируются по часам.

### 2.4. Безопасность
* **Авторизация:** проверка `Authorization: Bearer <token>` через `hash_equals()`.
* **Защита от SQL-инъекций и ошибок типов:** значения экранируются через `Bitrix\Main\DB\SqlHelper::forSql()`, ID приводятся к `(int)`. На входе используется `JSON_THROW_ON_ERROR` и приведение скалярных типов во избежание `TypeError` в PHP 8.2 (ограничение размера запроса и сетевая фильтрация делегированы Nginx).
* **Изоляция логов:** директория логов вынесена выше `DOCUMENT_ROOT` с правами `0750`.

## 3. Структура проекта

```text
local/
├── php_interface/
│   └── classes/
│       └── Integration/
│           └── Division/
│               ├── Logger.php               # Буферизированный логгер и ротация
│               ├── QueueRepository.php      # Работа с очередью в HL-блоке
│               └── DivisionBatchUpdater.php # Пакетная выборка и bulk-обновление
└── tools/
    └── 1c_import/
        ├── import.php                       # Webhook-приёмник для 1С
        └── worker.php                       # CLI-воркер для Cron
```

## 4. Настройка и запуск

1. **Автозагрузка:** подключить пространство имён `Project\Integration\Division\` в `/local/php_interface/init.php`.
2. **Highload-блок:** создать `DivisionImportQueue` с полями `UF_STATUS` (строка), `UF_PAYLOAD` (текст), `UF_CREATED_AT` (дата/время), `UF_ERROR_MSG` (текст).
3. **Токен:** задать параметр `1c_division_import_token` в настройках модуля `main`.
4. **Cron:** добавить запуск воркера раз в минуту (заменить на реальный путь в системе):
   ```cron
   * * * * * /usr/bin/php -f <путь к корню сайта>/local/tools/1c_import/worker.php >/dev/null 2>&1
   ```
